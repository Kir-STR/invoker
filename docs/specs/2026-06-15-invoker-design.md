# invoker — дизайн (spec)

Дата: 2026-06-15
Обновлено: 2026-06-17 — реориентация на 6-слойную agent-OS (см. §1).
Статус: operator-approved (сессия дизайна 2026-06-15; реориентация 2026-06-17)

## 1. Суть

`invoker` — Claude Code plugin, который разворачивает в произвольном проекте **небольшой переносимый agent-OS**: качественную универсальную основу для работы с AI-агентами. Набор файлов и процедур, дистиллированный из боевого проекта и очищенный от его специфики, чтобы работать в любом другом.

Шесть слоёв:

1. **`CLAUDE.md`** — ключевые инструкции основного агента (оператор).
2. **`AGENTS.md`** — роль советника (например, Codex как помощник).
3. **`GEMINI.md`** — роль ревьюера/контролёра в CI.
4. **`.claude/rules/`** — полезные правила, всегда в контексте (autoload), вынесены из `CLAUDE.md` ради его компактности.
5. **runbook-слой** — процедуры read-on-demand: не нужны в контексте постоянно и/или не пакуются в skills *(планируется)*.
6. **skills** — универсальные процедуры, **явно упомянутые** в `CLAUDE.md`/правилах, чтобы агент вызывал их наверняка, а не догадывался.

**Ключевое различие:** слои 1–5 scaffold'ятся в целевой проект; **skills живут в плагине и вызываются по имени** (в проект не копируются). Детерминированность вызова обеспечивает явная ссылка из rule/`CLAUDE.md` — в этом и смысл «использует наверняка».

Принцип: **рабочий инструмент сейчас, без оверинжиниринга**; не идеально-универсальный, но честный и переносимый.

Плагин состоит из двух родов сущностей:

- **Скиллы** (активная логика, живут в плагине): `invoke` (скаффолдер слоёв 1–5) и `retro` (движок эволюции правил). Команда `save` (тонкий триггер над памятью Claude Code) — отдельная plugin-команда (`commands/save.md`).
- **Шаблоны** (статика, которую `invoke` раскладывает в проект): инструкц-файлы, `.claude/rules/*.md`, seed-файлы.

> Канонические имена вызова — `/invoker:invoke` / `/invoker:retro` / `/invoker:save`; в прозе ниже сокращаем до `invoke` / `retro` / `save`.

Ключевое: `invoke` **не генерирует текст правил** — копирует выверенные шаблоны дословно. Вопросы `invoke` — **только про возможности плагина** (какие модули развернуть, под какие движки писать инструкции), не про значения проекта (имя/стек/конвенции). Где значение проектно-уникально и нет разумного дефолта — остаётся `{{placeholder}}` либо TODO-каркас, который оператор заполняет сам по месту.

### Граница с другими плагинами — самодостаточность

invoker **самодостаточен**: поставляет СВОИ процедуры-скиллы и не требует сторонних воркфлоу-плагинов. Это не «вендоринг чужого» — invoker сам и есть провайдер этих процедур. Поведенческие правила, где у проекта может быть свой готовый эквивалент (планирование, worktree-флоу), ссылаются на него формулировкой «или эквивалент», не привязываясь к конкретной реализации. Переносимо на Codex/Gemini.

## 2. Scope / Non-goals

В scope:

- 6-слойная модель: слои 1–5 scaffold'ятся в проект, слой skills живёт в плагине.
- Скилл `invoke` (скаффолдер) — **реализован**.
- Скилл `retro` (движок эволюции правил) — **реализован** как NL-оркестратор `skills/retro/SKILL.md` (порт из личной команды, пути → `.invoker/`).
- Команда `save` (триггер над памятью Claude Code) — **реализована** как `commands/save.md`; в скилл паковать нечего (вся логика в harness, только-Claude Code).
- runbook-слой — *планируется* (формат + как `invoke` его раскладывает).
- Каталог шаблонов (субстрат + модули) с уже снятой проектной спецификой.
- Декларативный реестр модулей `modules.json`.
- Multi-engine эмиссия инструкций (CLAUDE/AGENTS/GEMINI) без транспайлера.

Non-goals:

- Авто-перевод одной инструкции в три (multi-engine делается курируемыми ролевыми шаблонами).
- Авто-детект значений проекта, анкеты про проект, policy-engine.
- Поля реестра `requires` / `conflicts` / `maturity` — добавить, когда `invoke` начнёт ими пользоваться.

## 3. Архитектура

### 3.1. Анатомия плагина

```
invoker/
  .claude-plugin/plugin.json      # name, version, description
  skills/
    invoke/
      SKILL.md                    # invoke — NL-оркестратор скаффолдинга
      helper.mjs                  # тонкий CLI над ядром (resolve / apply)
      lib/                        # детерминированное ядро: registry → resolve → blocks → scaffold
      test/                       # node:test
    retro/
      SKILL.md                    # retro — NL-движок эволюции правил
      test/                       # node:test (структурный инвариант скилла)
  commands/
    save.md                       # триггер над памятью Claude Code
  templates/                      # дословно копируемая статика
    instructions/
      CLAUDE.md.tmpl              # роль: оператор
      AGENTS.md.tmpl              # роль: консультант
      GEMINI.md.tmpl              # роль: ревьюер
    rules/                        # по файлу на модуль (11)
      operator-gate.md  retro-loop.md  secret-hygiene.md
      worktree-workflow.md  pr-policy.md  review-loop.md
      subagent-dispatch.md
      safety.md  architectural-invariants.md  versioning.md  glossary.md
    seed/
      ideas_4_rules.md            # пустой inbox эволюции правил
      retro-template.md           # шаблон черновика ретро
  modules.json                    # РЕЕСТР модулей (control plane для invoke)
  README.md
```

`modules.json` лежит в **корне плагина**, не в `templates/`: это управляющий манифест, а не копируемая статика. Служебная зона `.invoker/` создаётся в **целевом** проекте (§4), частью плагина не является.

### 3.2. Реестр `modules.json`

Единственный источник правды для `invoke`. Вся «магия» зависимостей/групп/дефолтов живёт здесь, не в коде скилла.

Схема модуля:

```jsonc
{
  "operator-gate": {
    "title": "Operator gate",
    "group": "base-discipline",
    "default": true,
    "files": ["rules/operator-gate.md"],
    "depends_on": [],
    "note": "Подтверждение человеком перед необратимыми/наружу-направленными действиями."
  },
  "review-loop": {
    "title": "Review loop",
    "group": "git-pr-workflow",
    "default": false,
    "files": ["rules/review-loop.md"],
    "depends_on": ["pr-policy"],
    "note": "Нужен CI review-бот."
  }
  // … остальные модули
}
```

- `title` — метка для чеклиста `invoke`.
- `note` — **user-facing подсказка** рядом с модулем; НЕ вопрос про проект, НЕ авто-детект.
- `depends_on` — каскад, дотягивается автоматически.
- Поля `requires`/`conflicts`/`maturity` — пока не используются.

### 3.3. Слепок в целевом проекте `.invoker/modules.json`

`invoke` генерит в целевой проект отдельный артефакт (не копию реестра) для будущих re-invoke/upgrade:

```jsonc
{
  "plugin": "invoker",
  "plugin_version": "0.2.3",
  "engines": ["claude", "agents"],
  "selected_modules": ["operator-gate", "retro-loop", "secret-hygiene"],
  "resolved_modules": ["operator-gate", "retro-loop", "secret-hygiene"],
  "created_at": "…"
}
```

`selected_modules` (явный выбор оператора) и `resolved_modules` (после каскада зависимостей) разведены намеренно.

## 4. Каталог модулей

Модули наполняют слой **`.claude/rules/`** (слой 4). Слои runbook (5) и skills (6) — это не модули реестра, а отдельные сущности (§1).

### Обязательный субстрат («пустой invoker»)

Ставится всегда, без него invoker не invoker:

- инструкц-файл `CLAUDE.md` (+ `AGENTS.md`/`GEMINI.md` по выбору движков);
- каркас `.claude/rules/` + канон frontmatter (`globs` / `class`);
- служебная зона `.invoker/`: пустой `ideas_4_rules.md` (inbox эволюции правил) + слепок выбора `.invoker/modules.json` (пишется всегда); `retro-template.md` — только если выбран `retro-loop`. Реестр `modules.json` живёт в плагине (control plane `invoke`) и в целевой проект **не копируется**.

Субстрат не содержит ни одного поведенческого правила.

### Поведенческие модули (все опциональны)

Recommended-профиль (предотмечен в `invoke`, снимаем — не silent install): `operator-gate`, `retro-loop`, `secret-hygiene`.

| Модуль | Группа | Default | depends_on | Зависит от |
|---|---|---|---|---|
| operator-gate | base-discipline | ✓ | — | ничего |
| retro-loop | base-discipline | ✓ | — | ничего (identity feature) |
| secret-hygiene | base-discipline | ✓ | — | ничего |
| worktree-workflow | git-pr-workflow | — | — | git + worktrees |
| pr-policy | git-pr-workflow | — | worktree-workflow | PR-flow |
| review-loop | git-pr-workflow | — | pr-policy | CI review-бот |
| subagent-dispatch | subagent-workflow | — | — | subagent-driven стиль |
| safety | project-governance | — | — | safety-критичный проект (каркас) |
| architectural-invariants | project-governance | — | — | проект со слоистой архитектурой (каркас) |
| versioning | project-governance | — | — | контракты/схемы/документы |
| glossary | project-governance | — | — | — |

Каскад: `review-loop → pr-policy → worktree-workflow` дотягивается автоматически и показывается оператору.

### UX-группировка `invoke`

На диске — мелкие самодостаточные файлы-правила (переносимость + dependency graph). В диалоге `invoke` оператор не принимает 11 микрорешений: модули выбираются **пресетом** (single-select: только recommended / + git-PR-workflow / всё) либо своим набором. Группы:

- **Base discipline:** operator-gate, retro-loop, secret-hygiene *(recommended)*
- **Git/PR workflow:** worktree-workflow, pr-policy, review-loop
- **Subagent workflow:** subagent-dispatch
- **Project governance:** safety, architectural-invariants, versioning, glossary

`safety` и `architectural-invariants` — намеренно **каркасы** (заголовки + guidance + TODO), заполняются под проект вручную; см. §8.

## 5. Поток `invoke`

1. Оператор запускает `/invoker:invoke`.
2. `invoke` читает `modules.json`.
3. Спрашивает выбор модулей **пресетом** (single-select: только recommended / + git-PR / всё / свой набор); рядом `note`-подсказки. **Вопросов про проект нет.**
4. Выбор движков (capability-вопрос, multiSelect только по опциональным): `CLAUDE.md` всегда; `AGENTS.md` / `GEMINI.md` — по выбору (`CLAUDE.md` вариантом не выводится).
5. Резолв каскада зависимостей; результат показывается оператору.
6. Копирует выбранные `rules/*.md` **дословно** (`copyFileSync`, байт-в-байт) в `.claude/rules/`.
7. **Собирает инструкц-файл(ы)** из `templates/instructions/*.tmpl`: указатели на модули **уже встроены** в каждый engine-шаблон и размечены маркерами `<!-- module:<id> -->…<!-- /module -->`. `invoke` **вырезает** блоки невыбранных модулей. Текст не синтезируется — только включение/исключение размеченных блоков. `apply` форсит движок `claude` первым.
8. Раскладывает служебную зону `.invoker/`: пустой `ideas_4_rules.md` (всегда); `retro-template.md` (если выбран `retro-loop`).
9. Пишет `.invoker/modules.json` (слепок выбора). Валидация движков идёт **до** любых записей — частично инициализированный проект исключён.
10. Отчёт: что создано; напоминание заполнить TODO-каркасы (`safety`, `architectural-invariants`), если выбраны. Фактических `{{placeholders}}` в правилах не остаётся (см. §8).

## 6. Поток `retro` (движок эволюции)

1. Читает черновики-наблюдения по веткам из `.invoker/retro/<branch>.md` + наблюдения мастер-сессии.
2. Сводит кандидатов в `.invoker/ideas_4_rules.md` → «Активные кандидаты», с **n-счётом** (число независимых прецедентов) и целевым файлом. **Это единственное изменение ФС, которое `retro` делает по умолчанию.**
3. Для `n≥2` / high-conf-safety **готовит кандидата к промоуту**: proposed rule text + target file + rationale — и показывает в отчёте. **Фактическая правка `.claude/rules/*` / `CLAUDE.md` — только после явного подтверждения оператора.** Никакого автономного самопереписывания инструкций.
4. **Cleanup — gated.** По умолчанию черновики `.invoker/retro/<branch>.md` НЕ удаляются. `retro` предлагает cleanup; удаление разрешено только после записи строки в «Лог обработки» + подтверждения оператора. Альтернатива — архив (тоже явное изменение ФС).

Классификация кандидатов: `n≥2`/high-conf-safety → готов к промоуту; `n=1` → остаётся ждать; reject → строка в «Лог обработки»; move → spec/OPS.

> Решено (2026-06-17): `retro` пакуется как **скилл** (`skills/retro/SKILL.md`) — портируется из готовой личной команды `~/.claude/commands/retro.md` с заменой путей `.claude/` → `.invoker/`; `save` — как **plugin-команда** `commands/save.md`. Глобальные личные команды `/retro` и `/save` — «неправильный дом»; плагинные версии их замещают для проектов с invoker.

## 7. Multi-engine — без транспайлера

Инструкции под разные движки — это **три роли**, а не один текст в трёх форматах: CLAUDE = оператор, AGENTS = консультант, GEMINI = ревьюер.

- `templates/instructions/` держит три курируемых ролевых шаблона, каждый — с блоками всех модулей (`<!-- module:<id> -->`).
- `invoke` эмитит файлы только под выбранные движки.
- Авто-перевода одного в три нет — это оверинжиниринг.
- Описание проекта (имя/стек/конвенции) в шаблонах **не задаётся** — это не дело `invoke`.

## 8. Универсализация — работа авторинга, не логика `invoke`

Снятие проектной специфики делается один раз при написании шаблонов, не в рантайме:

- В каждом правиле дисциплинарный текст сохраняем дословно; проектную специфику заменяем на **разумный дефолт**, а не на плейсхолдер: `globs` → `**/*`, ветка → `main`, PR-инструмент → `gh`, бюджеты PR → числа (400/800/15), имя ревью-бота → обобщённое `review-bot` (с подсказкой заменить). После этого проектно-уникальных `{{placeholders}}` в правилах **не остаётся**.
- `safety.md` и `architectural-invariants.md` — самые проектные: вырождаются в **скелет** (заголовки-паттерны + guidance + блок «Как заполнять»), контент = TODO. Не переносим чужие доменные инварианты в произвольный репозиторий. Это TODO-разделы, не плейсхолдеры.
- `{{BRANCH}}` в `.invoker/retro-template.md` — единственный остающийся плейсхолдер; он **runtime**-плейсхолдер будущего `retro`, не для оператора.

`invoke` просто копирует уже-универсализованные шаблоны.

## 9. Открытые вопросы / отложено

- runbook-слой (5): формат + как `invoke` его раскладывает; какие процедуры из правил выносим. Критерий включения: правило слишком длинно для autoload, либо `retro` стабильно производит процедурный текст.
- Поля реестра `requires` / `conflicts` / `maturity`.
- Точная форма gated-подтверждений в скиллах (report+STOP vs интерактив).
